# The Duskbloods ultrawide executable analysis

The network-test executable contains a CPU perspective constructor that accepts an explicit floating-point aspect ratio and can derive it from independent width and height fields. It also contains separate width/height inputs for NVN presentation, texture allocation and DLSS. Two platform graphics-scale modes explicitly derive their crop width at 16:9. These findings make a small game-side override plausible. The work still needs to establish how the gameplay camera and scene-size policy feed these helpers, whether the active visibility tests share that camera, and whether the native reconstruction backend accepts 3440×1440.

Ghidra 12.1.4 ran headless in a scratch project. The logged MCP TCP endpoint was unreachable from the tool shell. SwitchLoader reported that it could not identify the GOT section, and whole-program autoanalysis stopped at its 210-second limit. I seeded the selected functions and checked decompiler results against AArch64 instructions and the NSO dynamic tables. In particular, I matched NVN indirect calls by following each resolver-name argument through its return-value store, then the module-relative data alias and the actual load and call. Decompiler parameter order and missing cross-references in this import require checking the ARM64 registers. The offsets below are relative to this Ghidra image base where labeled RVA. Buffer offsets and GPU virtual addresses in the [shader report](duskbloods-ultrawide-shader-analysis.md) belong to different address spaces.

## Scene dimensions, texture allocation and presentation

- **Platform dimension policy.** `0x71016c1af0` reads `nn::oe::GetOperationMode` and `nn::oe::GetCurrentGraphicsScale`, caching the latter at state `+0xc`. The notification handler `0x71016c1be0` re-reads it at `0x71016c1cc8`. That handler and operation-mode helper `0x71016c2000` derive a size pair from state and base dimensions at `0x7105b81a98/+4`. For scale states 1 and 2, the height is scaled by 4/5 or 2/3 with integer truncation, then width is computed as `(height * 16) / 9`. The other branch scales the two base axes separately by the mode-selected integer. The size pair reaches `0x71041552c0` at `0x71016c1e4c` and `0x71016c2130`. This is a crop policy with a graphics-scale input. It has not been tied to the dynamic scene rectangle. The checkout's graphics-scale service currently returns wire value 10, documented as scale enum 0. [Graphics-scale service](../src/core/hle/service/am/service/graphics_scale_controller.h).
- **Crop and size state.** `0x71041552c0` passes `(0,0,width,height)` to `nvnWindowSetCrop` at `0x7104155394` through data alias `0x7105a0ae50` and slot `0x7106b2e468`. It stores the pair on each window object at `+0x50/+0x54`, saves it at graphics-state `+0xf30/+0xf34`, and computes a common fit scale from the two ratios against reference fields at `+0x120/+0x124` of the first window record. This setter takes independent axes and does not resize the window textures in that crop update.
- **Present backing and queue.** `0x710491e5c0` passes two caller-supplied integers to `nvnTextureBuilderSetSize2D` at `0x710491e7ac`, obtains the texture storage size, allocates a pool for the requested image count, and creates each texture through `0x710491f240`. It passes those textures to `nvnWindowBuilderSetTextures` and initializes the window. `0x710491f0d0` submits the current index through `nvnQueuePresentTexture` at `0x710491f140`, then acquires the next one. Its caller includes a direct call at `0x7104159988`. The executable evidence reaches the NVN boundary. Lichii's VI2 handler independently decodes the guest packed last column/row and checks it against the registered layout. The SDK path from NVN crop and queue to that packed field, and any display-mode query that limits this title's allocation, remain untraced. [VI2 compositor and mode query](../src/core/hle/service/nx2_gsv.h#L2112).
- **Scene target binding.** `0x71040f3ae4` calls texture width and height getters, then sets a zero-origin scissor to those dimensions and binds render targets at `0x71040f3bcc/0x71040f3bf4`. This establishes one generic full-target binding path. It does not identify the 888×500 active gameplay viewport or the allocator for its 1920×1080 color, depth and motion backing. The game's dynamic resolution controller, gameplay target-layout policy and maximum texture or pitch restrictions remain open.

The bridge establishes independent output dimensions at network initialization and input dimensions at evaluation. The shader capture separately establishes the active input fields at prepass `c0+0x1e8/+0x1ec`, output width/height at output `c0+0x35c/+0x358`, and source last column/row at `+0x39c/+0x394`. The known axes are semantically consistent across the two layers. The intervening NVN/SDK code that packs these fields and builds the dispatch grids is still untraced. No native tiling granularity, maximum usable extent or acceptance of 3440×1440 follows from the two integer arguments. The scan also did not resolve the game-side caller that fills the optimal-range-constrained evaluation descriptor.

Frame 3330 used 888×500 active scene pixels and 1536×864 reconstruction output in a 1920×1080 backing. The later log records 1108×624 to 1920×1080 reconstruction and a separate 1920×1080 present crop. Those observations distinguish the active render size, output size, allocation and crop. They leave open how many game settings feed them.

The bound motion X factor at fragment `c3+0x40` in program `ca4beafaad0f3d62` is a separate dependency from the NVN motion-scale setter. Its shader-side value is 16/9 and Y is 1 in the captured draw. The ARM64 writer for that uniform and the source of its matrix remain unidentified. A wide mode must establish how the encoder's X/Y units, the reconstruction consumers and the current-to-previous transform agree before changing either scale. If the encoder preserves its captured aspect-based convention, X/Y becomes 43/18 and the corresponding normalized decode must account for the reciprocal. Confirm the signed scale against a controlled pan and the captured motion contract before treating that prediction as a patch value.

## UI layout

The two platform mode paths call `0x7101260b8c` at `0x71016c1e60/0x71016c2158` after updating the crop. This callback references `_OnSwapChainResized_forUIThread` at `0x710498576f`. On its UI-thread branch it queries a backing texture's dimensions and passes the packed pair into `0x7101246580` for active UI records. That function calls `0x710124676c`, then notifies UI objects when their sizes at `+0xac/+0xb0` change. This is evidence of a separate UI resize path. It does not establish a link to the late-draw slot-3 transform writer or a fixed logical UI canvas. The recorded coefficients of 1/1920 and 1/1080 remain shader-derived evidence. The actual compositor order, coordinate transforms and menu hit-testing still need correlation before assigning the HUD a centered `x=[440,3000)` rectangle.

## Reversible strategy and decision

1. Correlate one owner-launched gameplay frame with the [no-GDB execution trace](#no-gdb-execution-trace). Log the candidate descriptors, matrices and volume planes alongside the shader rows for `af80c123fbd8d4ef`. If the transforms cannot be matched directly, resolve the draw's bound vertex storage range and use a local GPU capture to find the preceding copy or compute producer.
2. If that correlation identifies one gameplay size/camera configuration, override those verified producers for this title and exact build behind a local switch. Keep vertical angle, depth mapping and camera pose fixed. Supply `43/18` at the shared aspect input or derive it from a same-aspect width/height pair. For a centered symmetric camera the horizontal projection coefficient becomes `32/43 ≈ 0.7441860465` times its 16:9 value. Regenerate the visibility planes and temporal matrices from the corresponding camera state, normalize jitter to the active render grid, and reset history at the mode change.
3. Allocate and present a genuine 3440×1440 output. Start with one fixed, same-aspect scene extent that the verified backend accepts. Set active viewport/scissor, color/depth/motion bounds, reconstruction input/output, history allocations and dispatch coverage coherently. Use separately verified UI transforms if retaining a centered 16:9 HUD. If native reconstruction rejects the network extent, isolate it with a verified reconstruction alternative or an available native 1:1 path before attributing the failure to projection or scene allocation.
4. Compare a static 16:9 reference and the wide frame at the same camera pose and vertical scale. Check that the central 2560×1440 region retains proportions and the two 440-pixel strips contain additional world geometry. Pan across the old edges to exercise visibility, motion and history, inspect the last columns for coverage, confirm the actual guest present extent, and check HUD alignment. Revert the switch and reproduce the baseline.

The constructor, allocation and NVN interfaces allow independent dimensions in the inspected code. There is no verified built-in arbitrary-aspect gameplay mode. A small configuration patch remains the first candidate if gameplay uses shared producers and the backend accepts the extents. If the fixed 16:9 crop branch or a separate scene policy runs after the override, or if native history and dispatch allocation reject the width, those boundaries need additional changes. A patch-site count or a claim of broader architectural changes would be premature until the gameplay writer and extent ownership are tied to a frame.

## Static call-chain follow-up

This pass used a read-only copy of the existing **Duskbloods UW** Ghidra project. The imported program and local NSO both matched the SHA-256 above. All addresses in this section are **RVAs in main**, build ID `14925e87e1acd4d5e9d071afeed230a1d4569f98000000000000000000000000`. The main executable's `.text` spans RVA `0x0–0x492768f`. The project contained 2,705 recognized functions, so I scanned the full text for aligned ARM64 `B/BL` targets, checked address-taking sequences and initialized data for selected entries, then disassembled the call sites and checked register handoffs. Indirect dispatch and other NSO modules remain outside the direct-branch census.

One candidate is a render-task path with a distinct camera and size payload. The direct caller at `456a688` in `456a2a0` enters `433dc80`. When input-state byte `+0xa36` (relative to the record at `render state +0xc170`) is set, `x6` points to the stack camera. ### Window backing, crop and scene extent

### No-GDB execution trace

Normal gameplay requires the Play Duskbloods launcher. The launcher appeared to reset Lichii's GDB settings. The CPU trace uses the running emulator's AArch64 Dynarmic backend and the existing Vulkan capture marker. It needs no debugger setting, socket or client.

- **Execution instead of memory interception.** On x64, Dynarmic can emit stores directly through fastmem or the inline page table. The A64 write callbacks and GDB watchpoint check see accesses that take the callback path. Watching a guest address there under default CPU settings cannot establish who writes the shader rows. A CPU alias, a copy from staging, or a GPU write also needs distinct evidence. [A64 x64 write emission](../src/dynarmic/src/dynarmic/backend/x64/a64_emit_x64_memory.cpp) and [memory fast paths](../src/dynarmic/src/dynarmic/backend/x64/emit_x64_memory.h).
- **Verified execution hook.** The existing Star Fox probe demonstrates substituting a breakpoint at Dynarmic's code fetch and handling its exception inside the emulator. The Duskbloods probe uses this mechanism at eleven known instructions. The NSO loader checks title `0400D1D02399A000`, the full 32-byte main build ID, the absence of an NCE patch collection, and the expected words at all eleven RVAs. The AArch64 Dynarmic backend installs the substitutions for the registered process. Runtime PC is `main load_base + RVA`. For example, the historical base `0x80b21000` would place `416abbc` at `0x84c8bbbc`. The probe reads the current loader base on each boot. The on-disk NSO and guest instruction bytes are untouched. Dynarmic treats the entry `PACIBSP` instructions as hints. The output hooks reproduce the replaced register/stack updates and execution continues without a debugger stop. [Loader](../src/core/loader/nso.cpp) and [trace sites](../src/core/arm/dynarmic/dusk_camera_trace.h).
- **Bounds.** Both `EDEN_DUSK_CAMERA_CPU_TRACE=1` and `EDEN_DUSK_CAMERA_TRACE` are required. The Vulkan marker's rising edge opens a CPU sampling window and delays the single shader capture by three renderer frame ticks. Sampling ends after the target frame or one second, whichever comes first, with at most 24 records per site per interval between renderer ticks. At most 1056 CPU records are logged per trigger across eleven sites. The translated sites still take the lightweight exception path for that opt-in process outside the window. Restart with the CPU flag cleared to remove that overhead. `capture_frame` is a correlation label for the window. CPU work and GPU submission can be queued several frames apart.
